# Pip — 设计决策记录

> 本文档记录 2026-09-22 一次设计讨论的结论。它解释**为什么**这么设计，`AGENTS.md` 里是**怎么做**的硬约束。

## 产品定义

一个打卡应用，只给自己和几个朋友用（个位数用户）。核心动作是「想打卡的时候在日历上标记一下」。

**明确不做**：提醒、通知、倒计时、连击天数、社交、排行榜。这决定了整个交互基调——安静、轻、低心理成本。

**关键用户特征**：所有人在中国大陆；手机为主；每人只看自己的数据；多设备同步是「可能想要」而非硬需求。

## 命名

**Pip**。骰子、骨牌上的那个小点就叫 pip，正好是「标记」的最小单位。选它的理由：短、好念、不撞同品类产品、气质轻，而且图标几乎不用设计——一个圆点就是全部。

slogan：`A pip a day.`

代码里统一用 `pip` 这个词（数据结构 `pips`、变量名、类名），让名字从交互里长出来，而不是贴上去。

**已排除的名字及理由**：Tally（知名记账 app）、Dotcal（dotcal.co 是日历产品，同品类相撞）、Notch（Minecraft 作者 + 刘海屏，搜索污染）、Ledger（硬件钱包）、Marked（前端 markdown 库）。

## 交互设计

因为**一天可能有多个打卡项**，「点一下日期就标记」不成立（点一下该标哪个？）。所以：

- **首页 = 汇总日历**。每个日期格子底部显示当天已打卡项的彩色小点，最多 3 个，超出显示 `+N`。
- **点某天 → 当天清单**。列出所有打卡项，逐个勾选，底部写当天备注。这是日常主入口，动线是：打开 → 看今天空着几个 → 点今天 → 勾完 → 关掉。
- **打卡项页**：管理标题、备注、图标、颜色、排序。点进单项看它自己的日历。
- **日历格子上的小圆点就叫 pip**，中文界面文案仍用「打卡」。

备注分两层：打卡项一个总备注（说明这是什么），每天可写一条（今天具体做了什么）——后者才是回头看时真正想看的。

## 数据模型

日期当 key，而不是存日期数组。这样判断「某天有没有打卡」是 O(1) 查表，渲染当月就是遍历 30 个日期各查一次。

```js
{
  version: 1,
  trackers: [
    {
      id, title, note, icon, color, sort_order, created_at,
      pips: {
        "2026-09-22": { note: "睡得很好", updated_at: 1790000000000 }
      }
    }
  ]
}
```

逻辑上按「记录」组织，物理上整块存。将来若数据大到卡顿再换 IndexedDB，只改读写层。

## 存储

**localStorage**。算过量：一条记录约 50 字节，5 个打卡项 × 一年 365 天 ≈ 90KB，用十年约 1MB，离 ~5MB 上限很远。不需要 IndexedDB。

key 布局：

```
pip:v1:data     → 整个数据库 JSON
pip:v1:backup   → 上一次写入前的旧值
```

- 加 `pip:v1:` 前缀：localStorage 在同一 origin 下所有页面共享，GitHub Pages 上同账号的第二个项目会共享配额和 key 空间
- 加 backup key：真正的风险是 `JSON.parse` 失败后应用显示成「空的」，用户一慌可能点保存把坏数据覆盖成真空数据。所以写之前先把旧值挪到 backup，启动时主 key 解析失败则回退 backup，**解析失败时绝不自动写回**，要提示用户
- `setItem` 必须包 try/catch（`QuotaExceededError`），失败时提示「存储写入失败，请立即导出备份」
- 检测无痕模式：写入失败要明确提示「请勿在无痕模式使用」

## 存储层抽象

**从第一天起就把存储层设计成返回 Promise 的异步接口**（内部就是同步 localStorage 包一层），界面只 `await store.load()` / `await store.save()`。

这是成本最低、收益最高的一条决定：将来换成云同步时只改这一个文件，界面一行都不用动。

## 导出 / 导入

导出/导入是**设备迁移**手段，不是同步。纪律：同一时间只在一台设备上打卡，换设备时才做一次迁移。

导出格式包一层外壳：

```json
{ "app": "pip", "version": 1, "exportedAt": "...", "data": { ... } }
```

导入时校验 `app` 和 `version`，提供「合并（并集）」和「覆盖」两种模式，**默认合并**（不会因手滑丢历史）。已知局限：并集无法传播「取消打卡」，这个语义漏洞接受即可——这也是每条记录要带 `updated_at` 的原因，将来可做「较新者为准」的合并。

导出按钮不能只是设置里一个入口，要做**主动提醒**：显示「上次导出：N 天前」，超过一个月变红。因为数据在浏览器里不在用户手里，清缓存/换手机/卸载就永久消失，你无法代为恢复。

## PWA

manifest + service worker，`name` 和 `short_name` 都填 `Pip`（三个字母，iOS 图标下不会截断）。

- service worker 的更新逻辑必须写对，否则 push 了新版本用户还是旧的（会被误判成部署失败）。做法：版本号 + 更新后提示「有新版本，点击刷新」
- **iOS 必须「添加到主屏幕」**：Safari 会清理 7 天内未访问网站的脚本存储，主屏幕应用被豁免。对一个可能一周没打开的打卡应用这是致命的
- iOS 主屏幕应用有**独立存储容器**，和 Safari 里是两份数据。必须引导用户统一只用主屏幕图标，别混用
- 分享动线：微信发链接 → 右上角「在浏览器中打开」→ 添加到主屏幕。建议应用内做一页图文说明，省得每个人问一遍

## 部署

GitHub Pages，**public 仓库**（免费账户只能从公开仓库发布 Pages）。仓库名 `pip`；若将来想让人搜到，用 `pip-app` 或 `getpip` 避开 Python 的 pip 搜索污染。

**发布前必做的验证**：拿手机在 4G 下打开一个 `github.io` 页面，再在微信里发给自己点开试试。这是 go/no-go——如果首次安装都装不上，方案作废。

**为什么 github.io 的国内速度不是致命问题**：PWA 把应用本体缓存到本地，装到主屏幕后日常打开不需要联网。所以可达性只在「首次安装」和「更新」两个时刻有影响。

## 域名

**用了 `github.io/仓库名/` 路径形式就不要再绑自定义域名**——换域名 = 换 origin = 旧数据读不到（旧数据还在，但应用够不着）。域名一旦发出去就定死，这是整个方案里最不可逆的决定。

## 备选路线（如果 Web 方案作废）

国内场景下，"把应用送到朋友手机上"这一步要么走微信（小程序备案，免费但需 1–20 个工作日，不用买域名服务器），要么走域名 ICP 备案（需国内服务器约 100–150 元/年 + 等 1–2 周）。

**小程序 + 微信云开发**是国内唯一同时满足「免费 + 速度快 + 跨设备同步」的组合。如果 GitHub Pages 的可达性验证失败，或将来「手机记了电脑看不到」真的成为痛点，转这条路线。

注意区分两种备案：小程序主体备案免费、不需域名服务器；域名 ICP 备案要买服务器。

## 实施顺序

按这个顺序做，每步都能跑，且早期成果不会因为后期卡住而白费：

1. 静态骨架 + 写死一个打卡项的日历网格
2. 接 localStorage，点击能标记并持久化
3. 打卡项列表 + 新建/编辑/删除
4. 当天清单 + 当天备注
5. 导出 / 导入
6. PWA（manifest + service worker）
7. 部署 + 4G/微信可达性验证
8. （将来）如需同步，把存储层换成云实现
